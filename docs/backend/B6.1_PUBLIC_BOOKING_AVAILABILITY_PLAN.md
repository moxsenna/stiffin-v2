## 3. Schema & Persistence: `availability_rules`

### 3.1 Table Definition
```sql
CREATE TABLE IF NOT EXISTS "availability_rules" (
  "id" UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  "organization_id" UUID NOT NULL REFERENCES "organizations"("id") ON DELETE CASCADE,
  "day_of_week" INTEGER NOT NULL CHECK ("day_of_week" BETWEEN 0 AND 6), -- 0=Sunday, 1=Monday, ..., 6=Saturday
  "start_time" TEXT NOT NULL CHECK ("start_time" ~ '^([01][0-9]|2[0-3]):[0-5][0-9]$'), -- HH:mm (24h)
  "end_time" TEXT NOT NULL CHECK ("end_time" ~ '^([01][0-9]|2[0-3]):[0-5][0-9]$'),   -- HH:mm (24h)
  "is_active" BOOLEAN NOT NULL DEFAULT true,
  "created_at" TIMESTAMPTZ NOT NULL DEFAULT now(),
  "updated_at" TIMESTAMPTZ NOT NULL DEFAULT now(),
  CONSTRAINT "availability_rules_time_order_check" CHECK ("start_time" < "end_time")
);

CREATE INDEX IF NOT EXISTS "idx_availability_rules_org_day"
  ON "availability_rules" ("organization_id", "day_of_week")
  WHERE "is_active" = true;
```

## 4. Slot Generation Engine (Pure Domain Architecture)

Located in `apps/platform-api/src/domain/flow/slots.ts` (100% pure TypeScript, no DB / no IO dependencies).

### 4.1 Inputs & Calculation Protocol
```ts
export interface GenerateSlotsInput {
  organizationTimezone: string; // e.g. "Asia/Jakarta"
  evaluationNow: Date;          // Current evaluation timestamp
  rangeFrom: Date;              // Query start UTC
  rangeTo: Date;                // Query end UTC
  serviceDurationMinutes: number; // Duration of candidate service
  weeklyRules: AvailabilityRule[];
  existingBusyIntervals: { startAt: Date; endAt: Date }[];
  bufferMinutes?: number;       // Default 30 min minimum notice
  slotCadenceMinutes?: number;  // Candidate slot interval, defaults to serviceDurationMinutes
}

export interface AvailableSlot {
  startAt: string; // ISO 8601 UTC
  endAt: string;   // ISO 8601 UTC
  localDate: string; // "2026-08-20"
  localDisplay: string; // "10:00 - 11:00"
}
```

### 4.2 Exclusion & Occupancy Rules
A candidate slot $[S_c, E_c)$ is excluded if:
1. It falls outside active `availability_rules` for the local weekday in the organization timezone.
2. It overlaps with any busy interval $[S_b, E_b)$ where $\max(S_c, S_b) < \min(E_c, E_b)$.
   - **Busy statuses**: `PENDING`, `CONFIRMED`.
   - **Terminal non-blocking**: `CANCELLED`, `NO_SHOW` NEVER block availability.
   - **Completed**: Blocks strictly during its actual interval $[S, E)$.
   - **Nullable `endAt` fallback**: If an existing booking has nullable `endAt`, its end is derived server-side as $S + \text{existingBooking.service.durationMinutes}$.
3. It starts before $\text{evaluationNow} + \text{bufferMinutes}$ (preventing past or unbuffered same-day bookings).

## 5. Double-Booking Concurrency Model (PostgreSQL Transaction Advisory Lock)

Empty slots have no row in the database to lock with `SELECT ... FOR UPDATE`. To genuinely serialize concurrent booking attempts:
1. **Advisory Lock**: Inside the creation transaction, the backend executes:
   ```sql
   SELECT pg_advisory_xact_lock(hashtext('booking_slot:' || $org_id || ':' || $local_day_str));
   ```
2. **Atomic Re-Check**: Re-query active overlapping bookings within $[S_c, E_c)$ inside the same locked transaction.
3. **Conflict Resolution**:
   - If overlap detected: transaction rolls back and returns stable `SLOT_UNAVAILABLE` (HTTP 409 Conflict).
   - If clear: proceed to create booking and commit.
4. **Verification**: Verified using true multi-connection concurrent PostgreSQL tests (2 independent `pg.Client` instances).

## 6. Public Contact Onboarding & Flow Interest Policy

When an anonymous user books via `/api/v1/public/:slug/bookings`:
1. Phone number is normalized to canonical E.164 via `normalizePhone(rawPhone)`.
2. Existing Shared Core `contacts` record in that organization is matched by normalized phone.
3. If new Contact:
   - Shared Core contact created (`name`, `phone_e164`, `email`).
   - Flow profile initialized with `interest = activeService.name` (deterministic non-empty requirement).
4. If existing Contact:
   - Preserves existing `interest` (does not overwrite unless empty).
   - Booking is attached to the existing contact.

## 8. Public Security, Rate Limiting & DTO Boundary

1. **Anonymous Safety**: Public routes do NOT require session authentication, but fail-closed if the workspace slug or service is invalid/inactive.
2. **Zero Client Authority**: Browser cannot supply `organizationId`, `priceAmount`, `amount`, `paymentStatus`, `status`, or `actorUserId`.
3. **Strict Public DTO**: Public responses only reveal public-safe fields:
   - Public Service: `{ id, name, category, durationMinutes, priceAmount, description }`.
   - Public Booking Created: `{ bookingId, status: 'PENDING', startAt, endAt, serviceTitle, amount }`.
4. **Rate Limiting**: Public endpoints enforce IP-based rate limiting (60 req/min for slots, 10 req/min for booking creation).
